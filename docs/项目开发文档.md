## 1. 项目概述

**一句话定位**：跨 AI 客户端的会话记录统一管理、检索与互迁工具。

**愿景**：让散落在各个 AI 客户端里的对话，成为可检索、可迁移、可共享的个人与团队资产——「你的 AI 工作史属于你，不属于任何一家厂商」。

**产品形态**：本地优先（local-first）的桌面应用 + 可选云端订阅服务。

**核心价值主张**（按优先级）：
1. **统一检索**——所有客户端的会话，一个搜索框（V2EX 2026 年 4/6/8 月三次独立出现的原帖痛点："想找以前问过的东西，不记得在哪问的"）
2. **原生格式互迁**——把会话从客户端 A 迁到客户端 B 继续用，双向、无时间/条数限制
3. **归档与共享**——本地/云端归档，团队会话库（企业知识管理）

## 2. 背景与问题定义

### 2.1 现状

多 AI 客户端并存已成为常态。以作者本机为例：Claude Code、Claude Desktop、OpenAI Codex CLI/Desktop、领慧AI工作台、WorkBuddy、小米 MiMo Desktop、deepseek harness 等 7+ 个客户端，各自独立存储对话记录。

### 2.2 三个核心痛点

| 痛点 | 描述 |
|---|---|
| **找不到** | 历史记录散落各客户端，跨客户端检索需挨家翻找，部分客户端（如旧版 DeepSeek 网页）连搜索都没有 |
| **带不走** | 换工具/换平台时对话无法带走；官方迁移通道限制重重（Codex /import 仅最近 30 天 50 条、单向只进不出） |
| **存不下/不能共享** | 客户端卸载即丢失；团队里"这个坑谁踩过"无法检索，新人重复踩坑 |

### 2.3 需求真实性证据

- V2EX 同款痛点帖 2026 年至少独立出现 3 次（1208907 / 1221070 / 1233053，最高 2406 点击），无人给出成品回复；
- 三大厂商 2026 年 3-9 月亲自下场做迁移（Gemini Import Chats、Anthropic Memory Import、OpenAI Codex /import 三次迭代）——需求被官方背书，但全部只做"搬进我家"；
- 角色扮演社区（SillyTavern 生态）自 2023 年起的跨平台对话迁移实践验证了技术可行性。

## 3. 竞品格局与差异化

### 3.1 格局：三条断层线 + 官方阵营，互不打通

| 阵营 | 代表 | 缺口 |
|---|---|---|
| CLI 编码工具线 | Tape（npm 实测累计仅 560 下载、3 个月未发版，濒临弃更）、continues、codex-plugin-cc | 无 GUI、不覆盖桌面客户端 |
| 浏览器扩展线 | AI Chat Exporter、MoveChat、AI导出鸭 | 只覆盖网页版，DOM 抓取，无反向导入 |
| 统一客户端线 | Cherry Studio、TypingMind、Chatbox | 只管"在我这聊的新对话"，不收编外部历史 |
| 官方阵营 | Codex /import（单向、30天/50条）、Gemini Import（5GB ZIP）、Hermes Import Session | 全部只做单向搬入，无中立工具 |
| 多 Agent 编排层 | Conductor（$22M A轮）、Claude Squad、Vibe Kanban 等 25+ 工具 | 拥挤红海，本产品明确不进入 |

重叠度最高的单点竞品：VS Code 插件 "Claude Code and Codex Assist"（agsoft，9,922 安装，含跨客户端续接），但绑定 VS Code、闭源、核心功能收费。

### 3.2 SessionHarbor 的差异化（四要素合一，市场空白）

1. **客户端中立**——不绑定任何 IDE/终端/厂商，独立桌面应用
2. **双向原生格式互迁**——不是 handoff 文档摘要，是写目标客户端私有格式落地，可继续对话
3. **国产与企业内部客户端覆盖**——MiMo、Kimi、领慧、WorkBuddy（公开互联网零竞品、零讨论）
4. **桌面级 GUI**——现有同类全是 CLI/Web

### 3.3 明确不做的（避坑清单）

| 不做 | 原因 |
|---|---|
| Agent memory / skill / 上下文层 | 红海：claude-mem 9万+ star、ai-memory、agentmemory 2万+，且官方（Codex /import）已连项目记忆一起搬 |
| 多 Agent 编排/并行管理 | 25+ 开源工具 + 2 家 YC 公司 + 官方 Agent View 亲自下场 |
| 跨设备会话续接（作为卖点） | 云电脑/Syncthing 同步会话目录是更直接的免费替代；企业用户大量跑 VDI。续接是迁移的自然结果，不是付费锚点 |
| "存储"本身作为卖点 | 字节是商品（iCloud/OneDrive 几块钱），付费锚点是流通/检索/共享能力 |

## 4. 产品范围

### 4.1 In Scope

- 多客户端会话的发现、聚合、增量索引（fs watcher）
- 跨全部已接入客户端的统一全文搜索（中文分词）
- 会话查看器（含 thinking、tool call/result、diff 的渲染）
- 双向迁移：读源客户端 → 中间格式 IR → 写目标客户端私有格式（含索引库回写）
- 导出：Markdown / JSON / HTML
- 会话分支（copy-on-branch 快照）
- 敏感信息扫描与脱敏（密钥/token/内网地址识别）
- 云端订阅（后期）：E2EE 同步、Web/移动阅读端、团队会话库

### 4.2 Out of Scope

- Agent 记忆管理、skill 管理、上下文注入（MCP 注入另议，属 V2+ 评估项）
- 消息发送/操控客户端（只读写存储，不驱动客户端行为）
- 云端会话的抓取（claude.ai / ChatGPT 网页对话不抓取，仅支持官方导出文件导入）
- 多 Agent 并行编排

### 4.3 双产品线（数据面物理隔离）

| 产品线 | 覆盖客户端 | 部署 | 说明 |
|---|---|---|---|
| **社区/商业版** | 公共客户端（Claude Code、Codex、Cursor、ChatGPT 导出等） | 本地 + 公有云 | 可开源、可商业化 |
| **企业内网版** | 领慧AI工作台、WorkBuddy、内部部署的 MiMo | 纯内网 | 零竞品主场；数据不出内网，与商业版代码同源、数据面隔离 |

## 5. 商业模式（Obsidian 模式）

| 层 | 定价 | 内容 |
|---|---|---|
| **本地层** | 永久免费（获客漏斗） | 聚合、统一搜索、互迁、导出、分支——对标 Tape/AgentsView 全免费，此层收费即无用户 |
| **云订阅层** | $5-8/月（锚点：Obsidian Sync $4-8/月；上限参照 aimemory.pro $14.99/月） | 全量 E2EE 同步、云端全文索引、Web/移动端优雅阅读（"读"的需求独立存在，Lyra Exporter 已验证） |
| **团队层** | 按席位 | 团队会话库：新人可搜"这个问题谁踩过"（AgentsView PG 团队同步已验证此方向） |

**付费叙事**：不是"会话记录的云端存储"，而是「**个人 AI 工作史成为可检索的资产**」。存储是载体，流通/检索/共享才是付费理由。

## 6. 系统架构

### 6.1 分层

```
┌─────────────────────────────────────────────────┐
│ 应用层   Electron GUI（会话列表/查看器/搜索/迁移向导）│
│          Web 阅读端（V2+）                         │
├─────────────────────────────────────────────────┤
│ 引擎层   纯 TS 核心（无 Electron 依赖，CLI 复用）    │
│          · 发现器（客户端自动探测）                   │
│          · 解析器（JSONL/SQLite → IR）              │
│          · 索引器（SQLite FTS5，chokidar 增量监听）  │
│          · 迁移器（IR → 目标私有格式 + 索引回写）     │
│          · 脱敏器（密钥/内网信息扫描）                │
├─────────────────────────────────────────────────┤
│ 适配器层 claude-code │ alink(领慧) │ codex │        │
│          workbuddy │ chatgpt-export │ ... 可插拔    │
├─────────────────────────────────────────────────┤
│ 中间格式 SessionHarbor IR（版本化 JSONL）            │
└─────────────────────────────────────────────────┘
```

### 6.2 数据流

- **索引流**：发现 → 解析 → IR → 本地索引（FTS5）→ GUI 展示（全程本地）
- **迁移流**：读源适配器 → IR →（脱敏过滤，可选）→ 写目标适配器（文件 + 索引库）→ 写前自动备份
- **同步流（V2）**：IR 加密（客户端公钥）→ 云端密文存储 → 其他设备解密

### 6.3 Local-first 原则

断网时核心功能（聚合/搜索/互迁/导出）完整可用；云端只做增强，不做依赖。

## 7. 中间格式（IR）设计

综合 SillyTavern 十年经验（Character Card V3 的版本化设计）与 OpenAI Responses API 的 items 模型（消息/工具调用/工具输出同为一流公民——官方演进方向，与 Claude Code/Codex 转录天然同构）：

```
SessionHarbor IR v1（一个会话 = 一个 .harbor.jsonl）
首行：{ "spec": "session-harbor", "specVersion": "1", "session": {...}, "extensions": {} }
后续：每行一个 Item

session: { id, sourceClient, sourceSessionId, title, createdAt, updatedAt,
           cwd, gitBranch, model, summary? }

Item 类型（type 字段区分）：
  message    { role: user|assistant|system, speaker?, content[], parentItemId? }
  tool_call  { callId, toolName, input }
  tool_output{ callId, output, isError }
  thinking   { text }（保留，迁回支持 thinking 的客户端时还原）
  file_ref   { uri, hash, kind }（附件外置引用，绝不 base64 内联——CharX 的教训）
  checkpoint { label, files[] }

extensions: { "命名空间/功能": {...} }  // 各客户端特有概念的降级存放处
```

设计铁律：
1. **版本字段 + extensions 命名空间 + 向下兼容双写**——中间格式三件套，缺一不可
2. **平台特有概念降级为消息流中可定位的片段**，不造专有顶层字段
3. **附件/工具产物外置引用**（IR 包目录 = 会话 jsonl + assets/）
4. 分支 = copy-on-branch 文件快照（SillyTavern 验证十年的方案）

## 8. 适配器规范（基于 2026-09-10 本机实测）

### 8.1 客户端存储格式实测结论

| 客户端 | 正文存储 | 索引 | 读 | 写（迁入） |
|---|---|---|---|---|
| **Claude Code** | `~/.claude/projects/<路径转义目录>/<uuid>.jsonl` | 无（文件即索引） | ✅ | ✅ 仅写文件 |
| **领慧AI工作台** | `%APPDATA%/alink/user/messages/<uuid>.jsonl`（+ `.prompt-navigation.json` 边车） | 无 | ✅ | ✅ 仅写文件 |
| **Codex** | `~/.codex/sessions/年/月/日/rollout-*.jsonl` | `state_5.sqlite` 的 threads 表（id/rollout_path/title/cwd/…）+ session_index.jsonl | ✅ | ⚠️ 写文件 + 回写 threads 行 |
| **WorkBuddy** | `~/.workbuddy/projects/<项目目录>/<uuid>.jsonl` | `workbuddy.db` sessions 表（drizzle 迁移管理，id/cwd/user_id/title/status/…） | ✅ | ⚠️ 写文件 + 回写 sessions 行 |
| **MiMo Desktop** | 云端（本地 db/*.db 正文表实测 0 行，仅 artifacts.db 等元数据） | — | 元数据只读 | ❌ 无法本地迁入 |
| **Claude Desktop** | claude.ai 云端（本地 731MB 全是应用与缓存） | — | ❌ | ❌ 仅支持官方导出 ZIP 导入 |
| **ChatGPT** | 官方 Data Export 的 conversations.json（树结构 mapping，需拓扑遍历） | — | ✅（导出文件） | ❌ 官方不支持重建 |
| **Cursor** | `~/.cursor/chats/*/store.db`（Tape 已验证可读） | — | ✅ | 待验证 |

关键格式细节（领慧 ↔ Claude Code 的互转是全项目最易闭环）：
- **领慧 = Claude Agent SDK 事件流 + 信封**：每行为 `{type, sessionId, timestamp, data}`，`data` 内即 Claude Code 原生事件结构。互转只需解/包一层信封。
- Claude Code 行结构：`{parentUuid, uuid, type, message, timestamp, cwd, gitBranch, …}`
- Codex 行结构：`{timestamp, type: session_meta|event_msg|…, payload}`

### 8.2 适配器接口

```typescript
interface Adapter {
  id: string;                       // "claude-code" | "alink" | ...
  discover(): Promise<ClientInstance[]>;   // 自动探测安装与数据目录
  listSessions(): Promise<SessionMeta[]>;
  readSession(id): Promise<HarborIR>;      // → IR
  writeSession(ir): Promise<WriteResult>;  // IR → 私有格式 + 索引回写
  capabilities: { read, write, incremental, live }
}
```

### 8.3 写回安全规约（本项目的最高风险点）

1. **写前备份**：目标文件与索引库先复制到 `.sessionharbor/backups/`
2. **运行检测**：目标客户端进程运行中（会话文件被锁/WAL 活跃）→ 拒绝写入并提示
3. **SQLite 回写**：仅在客户端关闭后操作；WAL/SHM 文件处理；事务包裹；失败即回滚
4. **配对保真**：tool_call ↔ tool_output 的 callId 配对完整性校验，缺失对降级为文本渲染并在迁移报告中标注
5. **schema 版本探测**：适配器内置已知 schema 指纹（如 WorkBuddy drizzle migration 版本），检测到未知版本 → 只读模式 + 警告（内部产品 schema 可能无通知变更）

## 9. 技术选型

| 项 | 选型 | 理由 |
|---|---|---|
| 语言 | TypeScript | 团队主栈；引擎层与 Electron/CLI 共享代码 |
| 桌面框架 | Electron（M2 起） | 生态成熟、Windows 11 主目标、团队 JS 栈；Tauri 2 作为后期减重选项 |
| CLI | Node CLI（M0 即用） | 引擎层直接复用，M0 无需 GUI |
| 本地索引 | node:sqlite（Node 22 内置）+ FTS5 trigram 中文分词 | 零原生依赖、内网友好；**实验特性警告待 ADR-001 决策**（锁 Node 版本 vs 换 better-sqlite3） |
| 增量监听 | node 内置 fs.watch + 节流（已实现，watch-smoke 通过） | 原计划 chokidar，实现时改用内置 fs.watch，零依赖；行为等价 |
| 加密 | libsodium（客户端密钥，服务端零知识）——M3 引入 | E2EE 是 v1 架构底线，不是 roadmap；协议设计见 N4/ADR-002 |
| 测试 | 现状：e2e（m0-e2e.mjs）+ bench（bench-index.mjs）两脚本；**Vitest 单测待引入（N3）**，fixtures 驱动对抗 schema 静默变更 | 承诺与现状的差距已登记在 §10.1 |
| 包管理 | pnpm monorepo | 引擎/适配器/CLI/GUI 分包 |

目录规划：

```
SessionHarbor/
├─ packages/
│  ├─ core/          # 引擎：IR、索引、迁移、脱敏
│  ├─ adapters/      # 每客户端一个子包
│  │  ├─ claude-code/  ├─ alink/  ├─ codex/  ├─ workbuddy/  └─ chatgpt-export/
│  └─ cli/           # harbor scan|search|migrate|export
├─ apps/
│  ├─ desktop/       # Electron（M2 起）
│  └─ web/           # 阅读端（V2）
├─ docs/             # 本文档迁入处 + ADR
└─ fixtures/         # 各客户端格式脱敏样本
```

## 13. 安全与合规

1. **E2EE 架构从 v1 开始**：密钥客户端生成、永不上传；服务端零知识，只见密文
2. **数据面隔离**：企业内网版与社区版共用代码、物理隔离部署，内部数据绝不出内网
3. **脱敏能力**：正则库识别 token/密码/密钥/内网 IP，云同步前可选脱敏
4. **只读原则**：默认只读扫描；写回仅发生在用户显式迁移动作中，且全程备份
5. **导入域名白名单**（若做 URL 导入）：防 SSRF（SillyTavern 同款实践）
